# 2026.288.0459 — feat(kubevirt-operator): install the platform onto a cluster charly did not create

## Summary

`candy/kubevirt-operator` installs KubeVirt + CDI correctly when the VENUE **is** a k3s guest: the
cluster is the guest, its kubeconfig is `/etc/rancher/k3s/k3s.yaml`, its client is
`/usr/local/bin/kubectl`. On a cluster charly did not create (OVH / GKE / EKS / on-prem) the recipe
served nobody — the hardcoded client path made a host venue impossible, and the node placement
KubeVirt injects could never be satisfied.

MEASURED on OVH `quant-dev` (3 nodes, k8s v1.35.2, whose nodes carry **no**
`node-role.kubernetes.io/*` label at all), KubeVirt v1.9.0 + CDI v1.66.1:

* `virt-operator` stayed permanently `Pending` on its static manifest's REQUIRED control-plane/master
  `nodeAffinity` — the existing master→control-plane rename does not cover it: the requirement is the
  **block**, not its spelling;
* after that, the operator's own install-strategy Job stayed `Pending` on the SAME requirement.
  Mechanism (kubevirt v1.9.0): `pkg/virt-operator/strategy_job.go:113` calls
  `placement.InjectPlacementMetadata(infraPlacement, …, RequireControlPlanePreferNonWorker)`, and
  `placement.go:41-92` applies that default ONLY while the CR's `spec.infra.nodePlacement` is unset.
  Declaring the placement suppresses it, and the whole control plane then reconciles to `Deployed`.

**Round 0's Block 2 uncovered a worse bug than the one it reported.** Executing the external branch
was impossible from authored configuration: `KUBECONFIG_IN_VENUE` had a non-empty default that
shadows every discovery arm, and **a consumer cannot override a candy `var:`** — `candy_vars` is the
wire field on `#InstallStepView` that the host passes the candy's own vars in, and `#Deploy` has no
env/var field. So on the host venue this change exists for, the operator's kubeconfig could not be
named by any `charly.yml`. The bed could never show this: its venue *is* the k3s guest.

Measured on this host rather than assumed:

```
$ sudo env | grep -E '^(HOME|USER|SUDO_USER|KUBECONFIG)='
USER=root   HOME=/root   SUDO_USER=atrawog        # and NO KUBECONFIG (sudo env_reset)
$ sudo ls -d /root/.kube/config /home/*/.kube/config
ls: cannot access '/root/.kube/config': No such file or directory
/home/atrawog/.kube/config
```

The default is now empty and the venue is DISCOVERED in a stated order: declared var →
`$KUBECONFIG` → `~/.kube/config` → **`${SUDO_USER}`'s kubeconfig** (a root step acting for the
operator — exactly what sudo reports) → a k3s venue's own file → else loud, naming all five.
