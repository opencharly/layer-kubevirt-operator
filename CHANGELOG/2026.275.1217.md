## Summary

Normalize the pinned KubeVirt operator manifest's removed `node-role.kubernetes.io/master`
label in-venue before `kubectl apply`, so the `check-kubevirt-operator` bed reaches
**zero warnings**. Fixes `opencharly/layer-kubevirt-operator#4`.

## RCA

The `check-kubevirt-operator` bed (`deploy:vm` on the disposable Arch k3s VM) reported
`warnings=1` at `deploy-add`. The warning is emitted by the GUEST's `kubectl apply` while
applying the pinned upstream KubeVirt release — not by any OpenCharly code:

```
Warning: spec.template.spec.affinity.nodeAffinity.…nodeSelectorTerms[1].matchExpressions[0].key:
  node-role.kubernetes.io/master is used; use "node-role.kubernetes.io/control-plane" instead
```

`node-role.kubernetes.io/master` was removed in Kubernetes 1.25; the pinned manifest still
schedules to it. **A repin cannot fix it** — measured: `v1.9.0` is the NEWEST KubeVirt release
and its `kubevirt-operator.yaml` still carries the label (2 occurrences); `v1.10.0+` do not exist.

## Change

Normalize the fetched manifest IN-VENUE before apply:

```
sed -i 's|node-role\.kubernetes\.io/master|node-role.kubernetes.io/control-plane|g' /var/lib/charly/kubevirt-operator.yaml
```

A **semantics-preserving RENAME** (same node-affinity/toleration intent). Modern clusters carry
only `control-plane`, so the renamed selector also *schedules correctly*.
