# 2026.269.1736 — fix(kubevirt-operator): run the KubeVirt + CDI applies IN-VENUE

fix(kubevirt-operator): run the KubeVirt + CDI applies IN-VENUE

**R1 — found while wiring the P6.5 beds.** The merged `layer-kubevirt-operator` candy
used **host-side** `kube: apply` steps. That cannot work for the R10 venue:

- The `kube:` verb connects from the **HOST** (`plugin-kube/cluster.go`'s `restConfig`
  → `$KUBECONFIG`/`~/.kube/config`) and reads its manifest from a **host path**
  (`methods.go`'s `runApply` → `readYamlDocs(in.Manifest)`).
- The R10 venue is a **k3s-server GUEST** whose kubeconfig lives in the guest
  (`/etc/rancher/k3s/k3s.yaml`).
- A composed candy cannot name a bed's host-side cluster profile without hard-coding
  that bed's name into the candy, coupling a reusable candy to one bed.

**The fix — the proven `candy/layer-helm-chart` precedent:** run every apply
**in-venue**, against the venue's OWN kubeconfig (`KUBECONFIG_IN_VENUE`, default
`/etc/rancher/k3s/k3s.yaml`) using the venue's own `kubectl`. This is exactly how
`layer-helm-chart` installs into a k3s guest, for the same reason: a candy that
installs into a *guest* cluster must run where that cluster's kubeconfig lives.

## Summary of changes (every diff item)

- **Manifest fetch, in-venue.** The four host-side `download:` steps
  (`kubevirt-operator-fetch`, `kubevirt-cr-fetch`, `cdi-operator-fetch`, `cdi-cr-fetch`)
  are replaced by two bounded in-venue `run:` fetches (`kubevirt-manifests-fetch`,
  `cdi-manifests-fetch`) that `curl` the pinned manifests into `/var/lib/charly/` in the
  venue (idempotent: skip when the file is already present and non-empty). The former
  `download:` verb wrote to a host path the in-venue step cannot read.
- **New bounded apiserver-ready wait** (`kubevirt-apiserver-ready`, added `2db0f53`,
  reworked `fdc63d7`): polls the guest's `kubectl get --raw /readyz` AND a Ready node
  before any apply — the k3s kubeconfig lands when the apiserver starts and the node
  registers moments later (the `k3s-kernel` candy may also reboot the guest), so a
  one-shot wait would error on an empty node list. Bounded, no sleeps.
- **The four applies, in-venue.** `kubevirt-operator-apply`, `kubevirt-cr-apply`,
  `cdi-operator-apply`, `cdi-cr-apply` become in-venue `command:` steps
  (`KUBECONFIG="${KUBECONFIG_IN_VENUE}"` + `kubectl apply -f /var/lib/charly/…` + a
  bounded `kubectl wait`/`rollout status`). The CR steps wait for the control-plane
  objects to EXIST before waiting on their rollout (the operator reconciles them
  ASYNCHRONOUSLY after the CR).
- **`context: [runtime]` → `context: [deploy]`** on the apply steps: these are
  deploy-time INSTALL steps (`kubevirt-installed` stays `[runtime]` — an idempotent
  post-install assertion).
- **New ADE check** `kubevirt-installed` (context `[runtime]`): the `virtualmachines.kubevirt.io`
  CRD is registered and `virt-api` is running in the venue (R3 — the candy that installs
  also asserts).
- **The `agent-check` is removed** (validator A1 item). It asserted that a
  `VirtualMachine` CR boots a KVM guest — i.e. the `deploy:kubevirt` *substrate's*
  behaviour, which is a DIFFERENT candy (`plugin-kubevirt`), not this platform-install
  candy. It also crossed into live-VM behaviour the R10 bed owns host-side. Its removal
  narrows this candy to its one responsibility (install + assert the platform), which the
  deterministic `kubevirt-installed` check now covers.
- **The host-side `kubevirt:` readiness probe lives in the BED's own plan**, which CAN
  name its per-deploy `kind: kubernetes` profile — the partition: install in-venue, probe
  host-side on the side that can name a profile.
